## Архитектурные принципы

### Почему LLM-Analyzer, а не Planner
Planner (детерминированный код) выбирал action жёстко по правилам, но LLM плохо следовала его директивам — игнорировала, переспрашивала уже известное, предлагала созвон не вовремя. Архитектура v3.0: убрали Planner полностью, дали Generator полный контекст (state_summary + RAG + промпт) — он сам решает что делать. Экономия 2-5 сек и ~$0.01-0.05 на сообщение.

### Детерминированная логика > промпт
LLM плохо считают и следуют жёстким правилам. Выносить в код:
- Счётчики (количество вопросов, попыток)
- Порядок действий (квалификация → созвон)
- Лимиты (макс 2 вопроса на тему)

### Confidence levels (используются в Extractor)
- `confirmed` — клиент явно сказал "хочу в Сочи"
- `mentioned` — клиент упомянул "слышал про Сочи"
- `null` — не говорил об этом

### Связанное извлечение goal + strategy
Клиент говорит "буду сдавать в аренду" → Extractor должен извлечь оба: goal: investment + strategy: rental. Не переспрашивать по отдельности.

## Принципы продаж (в промпте)

### ЭКСПЕРТ, НЕ ОБСЛУГА
София не соглашается с каждым возражением. Формула: прими эмоцию → контраргумент → покажи выгоду → оставь открытым. Без этой установки Generator по умолчанию "помогает" — соглашается с клиентом и сужает воронку до нуля.

### Баланс живого общения
Off-topic формула: `ОТВЕТ + мягкий переход к квалификации/созвону`.
- "Как погода в Сочи?" → "Сейчас +12 ☀️ Кстати, вы Сочи как вариант рассматриваете?"
- 1-2 ответа на off-topic + мягкий возврат. Если клиент болтает 2-3 раза — ок, он тоже человек.

### Два отказа — стоп
При 2 отказах от созвона — завершаем с подборкой материалов, не мучаем клиента.

### Холодные лиды — другой сценарий
RAG и промпт изначально заточены под горячих клиентов. Холодная база (не помнят заявку) требует:
- Этап АКТУАЛИЗАЦИЯ перед квалификацией
- Другую тональность и шаблоны приветствий
- Флаг lead_type (cold/warm/hot) в БД

### Лидоруб — паттерны cold outreach
Из скрипта продаж (Google Sheets, 6 табов):
- Объяснять ЗАЧЕМ спрашиваем: "объекты для инвестиций и для жизни сильно отличаются"
- При "пришлите цену": не отказывать, а мягко квалифицировать: "Конечно! Для себя или инвестиция?"
- При "позже/через полгода": узнать от чего зависит срок + предложить Telegram канал
- При "не помню заявку": не извиняться, а переформулировать: "В целом недвижимость интересна?"

### Финансовая экспертиза как инструмент
Бесплатная экспертиза = доверие. "Если бесплатно дают такой уровень, с ними можно работать."

### Честность про бота
Не врать что живой человек. "Разумный ассистент" + предложить живого эксперта. Доверие важнее конверсии.

## Открытые баги

### BUG-004: EN-раскладка → Extractor
Клиент написал "lkz bydtcnbwbq" (EN-раскладка = "для инвестиций"). Generator понял по контексту и ответил правильно. Но Extractor не распарсил → goal=null в state → при следующем сообщении переспросил.

**Причина:** Generator и Extractor — два независимых LLM-вызова. Generator видит всю историю. Extractor парсит конкретное сообщение буквально.

**Варианты:** (А) Автоконверсия EN→RU раскладки перед Extractor. (Б) Extractor учитывает предыдущий ответ Generator.

**Статус:** НЕ ИСПРАВЛЕН

## Технические уроки

### BUG-003: reasoning модели режут ответ
GPT-5.2 reasoning тратит часть токенов на внутреннее рассуждение. При max_output_tokens=800 ответ обрезался на полуслове.
**Решение:** Analyzer 300→1000, Generator 800→4000. **Правило: для reasoning моделей нужен 3-5x запас по max_output_tokens.**

### BUG-005: LLM должен видеть свои вопросы
Sofia спрашивает в greeting "Какая цель: отдых/доход/комбинированно?", клиент отвечает "доход", но LLM не видит своего вопроса → интерпретирует "доход" как вопрос о доходности.
**Решение:** save_message() greeting перед возвратом клиенту. **Принцип: LLM должен видеть свои собственные вопросы в истории.**

### BUG-002: Race condition
asyncio.create_task() → параллельная обработка → дубли ответов.
**Решение:** message_queue.py — lock + очередь, объединение сообщений. Lock = последовательность, очередь = все сообщения в одном ответе.

### Бан при массовой рассылке
~50+ сообщений за 30 минут с личного аккаунта = перманентный бан номера. 29 чатов мертвы.
**Правило:** Личный аккаунт + массовая рассылка = бан всегда. WABA — единственный легальный путь для массовых.

### Неверные цены = потеря доверия
В промпте были цены "от 5.2 млн", реальные — от 16.8 млн. Клиент приходит к менеджеру с ожиданием 5 млн — мгновенная потеря доверия.
**Правило:** Цены в промпте должны точно совпадать с актуальной базой застройщика.

### Коллизия user_id
hash(session_id) давал случайные числа, при рестарте Python менялся seed → другой user_id → переписки двух клиентов смешивались.
**Правило:** Никогда hash() для ID. Автоинкремент или детерминированные формулы.

## Чего НЕ делать (чеклист)

- **Не обрезать историю диалога** — LLM должен видеть ВЕСЬ диалог, не "последние 8 сообщений"
- **Не использовать gpt-5.2 с temperature** — не поддерживается
- **Не полагаться на LLM для счёта** — выносить в код
- **Не проверять WAIT по тексту** — только через state
- **Не добавлять общие слова в маркеры** — "записала" вызывает ложные срабатывания
- **Не хранить методы класса в dict** — перезапишутся через setattr
- **Не патчить промпт без cat** — названия секций могут отличаться от ожидаемых
- **Не рассылать >15 сообщений/день** с личного аккаунта — бан
- **Не предлагать канал которого нет** — WABA не подключен, не спрашивать "WhatsApp или Telegram?"
